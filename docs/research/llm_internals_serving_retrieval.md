# Technical brief: LLM internals, inference/serving, retrieval (prepared 2026-09-27)

Formulas and figures cite primary sources. [computed] = derived here from stated inputs. [unverified] = not checked against a primary source; do not teach as fact.

## Part A. LLM internals

- Tokenization: byte-level BPE merges frequent adjacent pairs until the vocab budget; guarantees no OOV. Llama 3 uses a 128K tiktoken-based vocab (https://arxiv.org/pdf/2407.21783). Tokens explain arithmetic/spelling weakness and why code and non-English cost more. KV cache and context are measured in tokens.
- Decoder block (Llama): RMSNorm -> causal self-attention -> residual -> norm -> SwiGLU MLP -> residual. Llama-3-70B: 80 layers, d_model 8192, 64 query heads, 8 KV heads, head_dim 128.
- Attention(Q,K,V) = softmax(QK^T / sqrt(d_k)) V (https://arxiv.org/abs/1706.03762). sqrt(d_k) keeps dot-product variance from growing with dimension and saturating softmax. Causal mask sets future positions to -inf, which is what makes the KV cache valid (past K/V never change). Naive cost O(n^2 d) time, O(n^2) memory per head.
- RoPE (https://arxiv.org/abs/2104.09864): rotate each 2-D pair of q and k by angle m*theta_i, theta_i = base^(-2i/d) (base 10000; Llama 3 uses 500000). Scores depend only on relative position (m-n). Extrapolation beyond training length still fails (low-frequency dims see unseen angles); fixes: Position Interpolation, NTK-aware scaling, YaRN (https://arxiv.org/pdf/2309.00071).
- KV cache bytes per token = 2 x n_layers x n_kv_heads x head_dim x bytes. [computed] Llama-3-70B FP16: 2 x 80 x 8 x 128 x 2 = 327,680 B = 320 KiB/token; 8,192 tokens = 2.5 GiB; batch 32 = 80 GiB (one H100). With MHA (64 KV heads) 8x larger. This is why GQA exists.
- MHA: per-head K,V. MQA: one shared K,V head. GQA (https://arxiv.org/abs/2305.13245): g KV heads shared by query groups; uptrained with ~5% of pretraining compute. MLA (DeepSeek-V2, https://arxiv.org/abs/2405.04434): low-rank latent compression of K,V; KV cache ~4-14% of MHA. GQA shares heads; MLA compresses what is stored.
- FlashAttention (https://arxiv.org/abs/2205.14135): tiles Q,K,V into SRAM blocks with online softmax; exact attention without materializing the n x n matrix. Bottleneck is HBM traffic, not FLOPs. FA-3 (https://arxiv.org/pdf/2407.08608): Hopper async, FP8, ~75% H100 utilization vs ~35% for FA-2.
- MoE: FFN replaced by N experts + router (top-k). Only active params computed; all resident in memory. Mixtral 8x7B ~47B total / ~13B active, top-2 of 8 (https://arxiv.org/abs/2401.04088). DeepSeek-V3 671B total / 37B active, 8 of 256 routed + shared experts (https://arxiv.org/abs/2412.19437). Concerns: load balancing, all-to-all comms, batch size to keep experts busy.
- Lost in the middle (https://arxiv.org/abs/2307.03172): U-shaped accuracy vs position of relevant info. Put the best chunks first/last; rerank; do not stuff the window.
- Decoding: greedy; temperature (divide logits by T); top-k; top-p nucleus (https://arxiv.org/abs/1904.09751); min-p (keep p >= min_p x p_max, https://arxiv.org/abs/2407.01082; disputed by https://arxiv.org/abs/2506.13681); beam search (bland for open-ended). Repetition penalties.
- Reasoning models: o1 (https://openai.com/index/learning-to-reason-with-llms/) showed test-time compute scaling. DeepSeek-R1 (https://arxiv.org/abs/2501.12948; Nature Sept 2025): pure RL (GRPO) with rule-based rewards produced self-verification and reflection without SFT; GRPO drops the critic by normalizing rewards within a group of samples (https://arxiv.org/abs/2402.03300). Levers: longer CoT, self-consistency, best-of-N with verifier, tree search. Reasoning tokens are billed and inflate latency.
- Structured output: constrained decoding compiles JSON schema/regex/CFG to an automaton and masks invalid logits; guarantees syntax, not semantics. Outlines (FSM), SGLang compressed FSM (https://arxiv.org/pdf/2312.07104), XGrammar pushdown automata, default in vLLM/SGLang/TRT-LLM (https://arxiv.org/abs/2411.15100; https://blog.vllm.ai/2025/01/14/struct-decode-intro.html). Providers implement strict tool schemas this way. Rule: function calling when the model decides WHETHER to act; response_format when you ALWAYS need a schema.

Interview Qs (A): why sqrt(d_k); why cache K,V but not Q; KV/token for 32 layers, 8 KV heads, hd 128, FP16 = 128 KiB [computed]; GQA vs MQA vs MLA one-liners; what RoPE encodes; why FlashAttention is exact yet faster; "47B params but runs like 13B"; top-p vs min-p; GRPO vs PPO; constrained decoding vs prompting for JSON.

## Part B. Inference and serving

- Prefill: whole prompt in one pass, large matmuls, compute-bound. Decode: one token per step, reads all weights + KV for few FLOPs, memory-bandwidth-bound; batching amortizes weight reads (https://arxiv.org/abs/2401.09670). Roofline: H100 ~990 TFLOPS BF16 / 3.35 TB/s = ~295 FLOPs/byte [computed]; below that is bandwidth-bound.
- Metrics: TTFT (queue + prefill), TPOT (per output token), ITL (inter-token gap distribution), E2E ~ TTFT + TPOT x (n_out - 1), throughput (tok/s), goodput = requests/s meeting both TTFT and TPOT SLOs (https://haoailab.com/blogs/distserve/). Throughput can rise while goodput falls.
- Continuous batching (Orca, OSDI'22, https://www.usenix.org/conference/osdi22/presentation/yu): iteration-level scheduling, sequences join/leave every step; selective batching. Chunked prefill interleaves prefill chunks with decode to bound ITL spikes.
- PagedAttention (vLLM, https://arxiv.org/abs/2309.06180): KV in fixed blocks (16 tokens) via per-sequence block tables, like virtual memory; prior systems wasted 60-80% of KV memory, vLLM <4%; 2-4x throughput; copy-on-write for parallel sampling.
- Prefix caching: vLLM hashes blocks by prefix; SGLang RadixAttention keeps KV in a radix tree with LRU (https://www.lmsys.org/blog/2024-01-17-sglang/). Hosted APIs expose this as prompt caching with discounted cached-input pricing; keep prefixes stable.
- Speculative decoding (https://arxiv.org/abs/2211.17192; https://arxiv.org/abs/2302.01318): drafter proposes gamma tokens, target verifies in one pass, rejection sampling preserves the target distribution. Works because decode is bandwidth-bound. Medusa (extra heads, https://arxiv.org/abs/2401.10774), EAGLE (feature-level drafting, https://arxiv.org/abs/2401.15077; EAGLE-3 3-6.5x). Gains collapse at high batch (compute-saturated) or low acceptance.
- Quantization: weight-only W4A16 GPTQ (https://arxiv.org/abs/2210.17323), AWQ (https://arxiv.org/pdf/2306.00978) shrink memory and speed low-batch decode; GGUF is llama.cpp's format. W8A8: SmoothQuant INT8 (https://arxiv.org/abs/2211.10438), FP8 (Hopper+) speed up prefill/high-batch. Activation outliers make activations harder than weights. FP8 KV halves KV memory. Always re-run task evals, not just perplexity.
- Disaggregated prefill/decode (DistServe OSDI'24, https://arxiv.org/abs/2401.09670): separate GPU pools, KV transferred over NVLink/RDMA; removes interference; Mooncake, NVIDIA Dynamo, vLLM/SGLang modes. Cost: KV transfer and orchestration.
- vLLM (breadth, PagedAttention, APC) vs SGLang (RadixAttention, structured output, DeepSeek serving) vs TensorRT-LLM (NVIDIA-only compiled engines, FP8/FP4 first, peak perf, slower iteration). [positioning is a synthesis]
- GPU memory = weights + KV + activations/workspace + ~1-2 GB CUDA context. [computed] Llama-3-70B FP16 = ~141 GB weights; on 2xH100 (160 GB) ~19 GB left = ~60K KV tokens; INT4 weight-only ~35-40 GB fits one H100 with ~110K KV tokens; FP8 (70 GB) leaves ~8 GB on one H100, so FP8 70B is usually 2 GPUs. vLLM gpu_memory_utilization default 0.9.
- LLM gateway: per-tenant RPM/TPM token buckets; retries with backoff+jitter only on transient errors, per-provider budgets; fallback chains and health-based routing (beware tool-call schema differences); exact and semantic caches (semantic is risky) and provider prompt caching; SSE passthrough, TTFT monitoring, backpressure, partial JSON parsing for tool calls; token/cost attribution, PII redaction; guardrails.

Interview Qs (B): why decode is bandwidth-bound; batching vs TTFT/TPOT and goodput; what PagedAttention solves; when speculative decoding stops helping; INT4 AWQ vs FP8 for high-QPS on H100; prefix caching and why long system prompts get cheaper; why disaggregate; memory for an 8B model, 16K ctx, 64 users, FP16: weights 16 GB + KV 64 x 16K x 128 KiB = 128 GiB [computed].

## Part C. Retrieval internals

- Chunking: fixed token windows with 10-20% overlap; structure-aware recursive splitting; semantic chunking; parent-child (retrieve small, return parent); late chunking. Anthropic Contextual Retrieval (https://www.anthropic.com/engineering/contextual-retrieval): prepend LLM-written 50-100 token context per chunk; top-20 failure rate 5.7% -> 3.7% (contextual embeddings) -> 2.9% (+ contextual BM25) -> 1.9% (+ reranking).
- Embeddings: bi-encoders trained with contrastive InfoNCE and hard negatives; Matryoshka truncation; cosine = a.b/(|a||b|); inner product = cosine for L2-normalized; |a-b|^2 = 2 - 2cos. Use the metric the model was trained with; query/passage prefixes matter. MTEB leaderboard.
- BM25: score(D,Q) = sum_t IDF(t) * f(t,D)(k1+1) / (f(t,D) + k1(1 - b + b|D|/avgdl)), Lucene IDF = ln(1 + (N - n_t + 0.5)/(n_t + 0.5)); k1 ~1.2-2.0 (TF saturation), b ~0.75 (length normalization). Strong on exact identifiers and rare tokens; weak on vocabulary mismatch.
- Hybrid: dense (semantics) + sparse (BM25, SPLADE). Reciprocal Rank Fusion RRF(d) = sum_i 1/(k + rank_i(d)), k = 60 (Cormack et al. SIGIR 2009); rank-based, no score normalization. Alternative: convex combination of min-max normalized scores.
- Rerankers: cross-encoders score (query, passage) jointly; O(candidates) passes so used on top 50-200. BGE-reranker, Cohere Rerank; ColBERT late interaction (MaxSim) as middle ground; LLM listwise rerankers strongest and most expensive.
- HNSW (https://arxiv.org/abs/1603.09320): multi-layer proximity graph; greedy descent from top layer, beam of width efSearch at layer 0. M = degree (recall and memory up), efConstruction = build quality, efSearch = query recall/latency (>= k). Only M affects memory. Memory ~ 4d + ~8M bytes/vector (float32, int32 links). [computed] 768-d, M=16: ~3.2 KB/vector; 100M vectors ~320 GB RAM, hence PQ/SQ or DiskANN. Deletes are tombstoned and degrade the graph.
- IVF: k-means into nlist cells (nlist ~ C*sqrt(N)); probe nprobe centroids. PQ: m subvectors, 256-entry codebooks -> m bytes/vector, table lookups (ADC). [computed] 768-d at m=64 = 64 B vs 3,072 B raw (48x). Refine with exact vectors. IVF needs training and misses at cluster boundaries; HNSW better recall/latency but high memory, slow inserts; IVF-PQ for billion scale on limited RAM; GPU (Faiss GPU, cuVS/CAGRA). https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index
- Filtering: pre-filter is exact but selective filters fragment the HNSW subgraph; post-filter returns < k or empty; single-stage filtered ANN integrates the predicate (Pinecone single-stage, Weaviate ACORN, Qdrant payload-aware links). Ask what fraction survives the filter; very selective filters often fall back to brute force [thresholds vendor-specific].
- Permission-aware retrieval: ACLs as metadata filters at query time plus re-check at result time; sync on change events; per-tenant namespaces for hard isolation; never rely on the LLM to enforce access; over-fetch to compensate for late-binding rejections; don't leak existence via counts.
- Citations: return chunk ids/spans; cite by id; verify post hoc (string match or NLI faithfulness); metrics: citation precision/recall, faithfulness (RAGAS, ARES).
- Freshness: batch vs streaming upserts; HNSW tombstones; IVF retrain on drift; store doc version/hash and embedding-model version (never mix models in one index); define a freshness SLO.
- Metrics: recall@k, precision@k, MRR = mean 1/rank_first_relevant, nDCG@k with DCG = sum (2^rel_i - 1)/log2(i+1); hit rate; BEIR (https://arxiv.org/abs/2104.08663). Measure retrieval and generation separately.
- Agentic RAG: HyDE (https://arxiv.org/abs/2212.10496), multi-query, step-back, decomposition; multi-hop IRCoT (https://arxiv.org/abs/2212.10509), Self-RAG reflection tokens (https://arxiv.org/abs/2310.11511); retrieval as a tool the agent re-queries, gated on confidence.
- GraphRAG (https://arxiv.org/abs/2404.16130): LLM-extracted entity graph, Leiden communities, pre-summarized; global sensemaking via map-reduce over community summaries; heavy indexing cost; local mode for entity neighborhoods.
